## What is being reviewed and how

Writing the task list for step 8 of the implementation order (delivery data and stats: releases, GitHub Actions runs and the DORA proxies) found places where the specs were silent or could not be built as written. The fetch spec had no `Release` or `WorkflowRun` record, said nothing about how a sync tells that releases or runs are unchanged, and proposed a `created` filter for workflow runs that GitHub caps at 1,000 results. The stats spec named the delivery metrics without saying what each counts, in which unit or when a DORA proxy counts as configured, and mapped `star_events` to the delivery group while listing stars under activity. The reports spec had no delivery sections. Step 8 also carried stars, forks, watchers and languages, whose fetch resources were never specified. The amended specs settle all of this so the task list has no "decide with the user" tasks. None of the items below is a decision that needs your answer before the list runs: each is a choice made on the specs' own logic and is reversible. Approve or flag each; a flagged choice changes the spec paragraph and the task named under it before the list runs.

## Choices made (approve or flag)

1. **Stars, forks, watchers and languages move to a new step 10.** Their fetch resources were never specified (stats review 1 left them open), GitHub records when a star or fork was made but not when someone started watching, and step 8 with them was more than the fifteen tasks a list should hold. Step 10, "Popularity data and stats", is added to the implementation order, to be specified with its own task list; steps 9 and 10 are independent. Until then the four stay in `tables['unavailable']`, with the reason naming step 10. (Implementation order; task 9)
2. **The delivery group reads pull requests, releases and workflow runs.** `resources_for('delivery')` was `{releases, star_events, workflow_runs}`; stars are not delivery, and the lead-time and hotfix proxies read pull requests. It is now `{pull_requests, releases, workflow_runs}`; `star_events` stays in `RESOURCES`, unbuilt, for step 10. The default groups stay `activity,flow`, so the default report's cost does not change; delivery is asked for with `--groups`. (Stats spec API; fetch spec API; task 9)
3. **Records.** `Release` holds `repo`, `tag_name`, `created_at`, `published_at` and `is_prerelease`, for published releases only: drafts are visible only to tokens with push access, so storing them would make the cache depend on whose token filled it. `WorkflowRun` holds `repo`, `id`, `workflow_path`, `name`, `event`, `head_branch`, `status`, `conclusion`, `created_at`, `updated_at`, `run_started_at` and `run_attempt` (the list returns each run's latest attempt). (Fetch spec API; task 1)
4. **Pull request labels and first commit.** `PULL_REQUESTS` also selects the first 20 labels and the first commit's `authoredDate` (a pull request's commits are listed oldest first). More than 20 labels keeps the first 20, an accepted limit. `authoredDate` is used, as in `activity`, so a rebase does not reset the lead time; a pull request with no commit falls back to its `created_at`. Adding a label moves the pull request's `updatedAt`, so the incremental read sees it. (Fetch spec Incremental sync step 2; tasks 1 and 2)
5. **Releases are read in full when a listing probe changes.** Releases can only be paged by creation time, and a release published from an old draft, which release-drafting workflows keep, would be missed by a stop-at-the-watermark read. Releases are few, so every read is a full read that replaces the repo's rows. The repo listing also selects the release count and the newest-created release's `updatedAt` (about 1 point more per 100 repos); a repo's releases are skipped when that text equals the one stored in a new `sync_state.probe` column and no full re-read is due. An edit to an older release is seen at the next full re-read (`fetch.full_refresh_after`, 30 days by default), an accepted limit. (Fetch spec Incremental sync steps 1, 2 and 5; tasks 1 to 3)
6. **Workflow runs: an unfiltered REST list with a free 304.** The spec's `created=>watermark` filter caps the result at 1,000 runs (Automatic checks), so the list is requested without filters, newest first, 100 per page. The first page goes through the ETag store, so an unchanged repo costs a 304, which does not count against the rate limit; an incremental read stops at the first run created before the watermark less `fetch.overlap`. The watermark is the `Date` header of the first page's response, through a new `RestResponse.date`. Each cached run that is still not `completed` and was not on the pages read is re-read by id, and a 404 there removes it (the implementation order's "in-progress runs are refreshed on the next sync"). A 404 on the list is read as no runs, so one repo without Actions data cannot fail an organisation's sync. GraphQL has no probe for runs, so a repo synced for `workflow_runs` is never skipped outright, at no rate cost when unchanged. (Fetch spec Incremental sync steps 1 to 3 and 5; tasks 3 and 4)
7. **All run history is fetched.** The first sync reads every run, so a repo with N runs costs about N/100 REST requests once (the REST budget is 5,000 an hour, and `fetch.on_rate_limit` `wait` rides out the limit). No history window is added; `--since` limits the report, not the fetch. Flag this if you want a setting that bounds the backfill. (Fetch spec Incremental sync step 2; task 4)
8. **Cache schema 3, no migration.** The new tables and columns raise `SCHEMA_VERSION` to 3 and change the listing and `PULL_REQUESTS` query hashes, so a step 6 or 7 cache is refused once with the existing `CacheVersionError` message, as at step 6. (Fetch spec Cache; tasks 1 and 11)
9. **`cache info` and the sync log name the new resources.** `CacheInfo` gains `releases` and `workflow_runs`; the sync log already gives rows per resource. (Fetch spec API, reports spec `cache info`; task 10)
10. **Actions metrics.** `workflow_runs` counts every run by `created_at`. `workflow_success_rate` is `success` over the completed runs whose conclusion is `success`, `failure`, `timed_out` or `startup_failure`; cancelled, skipped, neutral, action-required and stale runs say nothing about the code and are left out. `workflow_duration_p50` (and a `p90`, as in flow) is `updated_at - run_started_at` in a new unit, `minutes`, because runs take minutes and hours would print as `0.1`; it is a proxy, since GitHub's per-run timing endpoint would cost a request per run. (Stats spec Metric groups; task 6)
11. **Release metrics.** `release_count` counts published releases by `published_at`, prereleases included. `release_interval_days` is renamed `release_interval_p50`, like the other percentiles: the `median_low` of the whole days between consecutive releases of the same repository, bucketed by the later one, so it is one real interval and an integer, as the JSON output requires of unit `days`. (Stats spec Metric groups; task 6)
12. **What a deployment is.** With `stats.deploy_workflow` set, a successful completed run of the workflow whose file name (`deploy.yml`) or name equals the setting, at the time it finished; matching the file name as well as the name keeps working when a workflow sets a per-run `run-name`. Without it, a release that is not a prerelease. (Stats spec Metric groups and Settings; task 7)
13. **"Configured" means the inputs exist in the cache.** `stats.hotfix_labels` defaults to `['hotfix']`, so a setting alone cannot tell whether a repository follows the convention, and a 0% change failure rate for a repository that never labels hotfixes would mislead. `deployments` and the lead time are emitted when the subject has at least one deployment in the cache; the change failure rate when it also has at least one hotfix pull request; time to restore when it has a hotfix pull request. Otherwise each is a row in `tables['unavailable']` saying what is missing. (Stats spec Metric groups; task 7)
14. **Lead time.** From a merged pull request's first commit to the first deployment of the same repository at or after its merge, bucketed by the deployment. Whether that deployment contains the merge commit is not checked (it would cost a compare per pull request), which is why it is a proxy. (Stats spec Metric groups; task 7)
15. **Change failure rate and time to restore.** A deployment failed when a hotfix pull request of the same repository was opened after it and within `stats.failure_window`; a deployment whose window is still open counts as not failed. Time to restore is a hotfix pull request's open-to-merge time, bucketed by its merge. (Stats spec Metric groups; task 7)
16. **A user subject's delivery counts the whole repository.** For a `user` subject, `activity` and `flow` count only the user's own commits, pull requests and issues; `delivery` counts every release, run and pull request of the user's repositories, because a release ships the repository's work, and a lead time on the user's own pull requests only would leave out what the release shipped. (Stats spec Aggregation; task 8)
17. **No delivery breakdowns.** Delivery has total series only, like flow. (Stats spec Aggregation; task 8)
18. **Reading the cache for delivery.** Releases are read whole (an interval and a lead time reach back before the range), runs from a day before the range (all of them when `stats.deploy_workflow` is set, for the same reason), and pull requests whole, only when a proxy needs them. A `None` `since` starts at the earliest release or run, not the earliest pull request, when only `delivery` is asked for. (Stats spec Range and Reading the cache; task 8)
19. **Terminal layout.** Two tables after flow: Delivery by period (Runs, Success as a percentage, Duration p50 and p90 in minutes, Releases, Release interval p50 in days; a `Total` row sums Runs and Releases only) and DORA proxies by period (only the columns of the proxies emitted; a `Total` row sums Deployments). The trend lines gain `workflow_runs`, `release_count` and `deployments`; ratios get none. (Reports spec Terminal; task 10)
20. **HTML layout.** A Delivery section after Flow, with tiles (Workflow runs, Success rate, Releases, and Deployments and Median lead time when emitted), per-period charts (ratios as 0 to 100 per cent on a fixed axis), the same two tables per granularity, and a line saying the DORA figures are proxies explained in the README. (Reports spec Static HTML; task 11)
21. **One task list, in `agents/tasks/stats/`.** As at step 6, the list lives with the spec whose group it builds, as `stats/tasks-3.md`, and carries the fetch and reports work the group needs.
