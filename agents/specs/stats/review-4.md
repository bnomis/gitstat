## Decision

1. **Where stars, forks, watchers and languages live in the report.**
   - *What is being decided.* Whether the four stay `activity` metrics, as the stats spec has listed them since 1.0, or become a `popularity` group of their own, and if so whether that group is on by default.
   - *Background.* The stats spec has listed them under `activity` since 1.0 (2026-10-29), and they have been rows in `tables['unavailable']` since step 4 (stats review 1, choice 2), because nothing fetched them. The implementation order's step 10 entry (2026-10-30) left open "the `activity` metrics step 4 left unavailable, or a group of their own if the spec moves them there". `activity` is the default group with `flow`, and it is author-centred: for a `user` subject it counts only the user's own commits. A star or a fork belongs to a repository, like a release in `delivery` (stats review 3, choice 16). The star and fork histories are the costliest data wambatic reads after commit history: a first sync costs one GraphQL point per 100 stars and one REST request per 100 forks, for every repository of the subject (choice 8).
   - *What it affects.* `GROUPS` and `resources_for` in the stats spec, the default cost of `wambatic report` and of the web app's pages, the user-subject rule, where the terminal and HTML sections go, and tasks 7 to 11.
   - *Option A (recommended): a new `popularity` group, asked for with `--groups`.* The default stays `activity,flow`, so a default report costs what it does today plus about one GraphQL point per 100 repositories for the counts the listing carries (choice 1). The four leave `activity` and its unavailable rows; the group has its own terminal tables and HTML section after delivery, counts every star and fork of a user's repositories, and runs with `--groups popularity` or `--groups activity,flow,popularity`. This is how the specs and the task list are written now.
   - *Option B: keep them in `activity`.* Every default report syncs `star_events` and `forks`: the first report of a popular organisation pays the whole star and fork backfill before it prints commits, and later ones pay the incremental reads. The user-subject rule has to make an exception inside `activity` (own commits but all stars). Changes tasks 7 to 11 (no new group; the activity tables gain the popularity columns) and the README.
   - *Option C: a new `popularity` group, on by default.* As A, with the default becoming `activity,flow,popularity`, so every default report pays the backfill as in B, but the group's sections stay separate. Changes `StatsRequest.groups`, the `--groups` help, task 7 and the README; every test that relies on the default groups would need the popularity fixtures.
   - Asked on 2026-10-30 as a decision card in the project thread; the answer is copied below.

## Choices made (approve or flag)

1. **Counts and languages come with the repository listing.** The listing every sync reads gains `stargazerCount`, `forkCount`, `watchers { totalCount }` and the 20 largest languages with `totalSize`, stored on the repo row. That costs about one GraphQL point more per 100 repositories, on every sync whatever its resources, and keeps the counts as fresh as the last sync without a per-repo request. The listing's query text changes, so its hash changes (choice 9). (Fetch spec Incremental sync step 1; tasks 1 and 2)
2. **Watchers are a current count only.** GitHub records no time of watching, so there is no watchers series; the count is GraphQL's `watchers { totalCount }` (users subscribed to the repository, what GitHub's interface calls watchers), never REST's `watchers_count`, which is the star count under an older name. (Fetch spec Incremental sync step 2; stats spec popularity; tasks 1 and 6)
3. **Languages are a snapshot of the 20 largest per repository.** GitHub keeps no history of a repository's languages, so they are a table, not a series. Each repository keeps its 20 largest languages by bytes, and the bytes of the rest (`totalSize` less the 20) are summed into one `Other` row over the subject; the table's `share` is each row's bytes over all bytes. Bytes are what GitHub's linguist reports, so vendored and generated files GitHub does not exclude are counted, like the line counts in `activity`. (Fetch spec Incremental sync step 1; stats spec popularity; tasks 2 and 6)
4. **Stars from GraphQL, keyed by the stargazer's node id.** `STARGAZERS` pages `stargazers` newest first by `STARRED_AT`, with each edge's `starredAt` and the user's `id`. The node id is non-null and survives a rename, and no login is stored, since no metric needs one. (Fetch spec Incremental sync step 2; tasks 2 and 3)
5. **Forks from the REST fork list.** GraphQL's `forks` connection filters by owner affiliation with a default of owner and collaborator, and its schema does not say what that keeps for forks owned by other people, while REST "List forks" is plainly the repository's direct forks, newest first. Forks use the REST budget, which also spreads the cost. The live test checks the cached forks against the listed count (fetch spec, Testing). (Fetch spec Incremental sync step 2; task 4)
6. **Probes on the listed counts.** A repo's stars (forks) are skipped when the listed `stargazerCount` (`forkCount`) equals the one stored in `sync_state.probe`, as releases are skipped on their probe since step 8. A star added and another removed between two syncs leave the count unchanged and are seen at the next full re-read (`fetch.full_refresh_after`, 30 days by default), an accepted limit. `forkCount` counts the whole network, so a fork of a fork costs one read that finds nothing. (Fetch spec Incremental sync step 1; tasks 3 and 4)
7. **A falling count means a full read.** An incremental read (newest first, stopping at the watermark less `fetch.overlap`, as for pull requests) cannot see a removed star or a deleted fork; when the listed count is below the stored one, the read is a full read that replaces the repo's rows, so a removal leaves the cache at the next sync (the implementation order's "a removed star leaves the cache on the next sync"). (Fetch spec Incremental sync steps 2 and 5; tasks 3 and 4)
8. **The whole history is fetched.** The first sync with `--groups popularity` reads every star and every fork: about one GraphQL point per 100 stars and one REST request per 100 forks per repository, so a repository with 100,000 stars costs about 1,000 points of the 5,000 an hour, and `fetch.on_rate_limit` `wait` rides out the limit, as for workflow runs (stats review 3, choice 7). No history window or cap setting is added. Whether GitHub stops paging very long stargazer or fork lists could not be checked from this session (see Open); flag this if you want a setting that bounds the backfill. (Fetch spec Incremental sync step 2; tasks 3 and 4)
9. **Cache schema 4, no migration.** The new tables and repo columns raise `SCHEMA_VERSION` to 4 and change the listing queries' hashes, so a step 8 or 9 cache is refused once with the existing `CacheVersionError` message, as at steps 6 and 8. (Fetch spec Cache; tasks 1 and 9)
10. **Four series.** `stars_added` and `forks_added` count the stars and direct forks made in each bucket; `stars_total` and `forks_total` count those made on or before each bucket's last day. They count the stars and forks that exist now, by when they were made: a removed star is in no bucket, so a cumulative series never falls and can read below what GitHub showed at the time. The README says so. (Stats spec popularity; task 6)
11. **Two tables.** `tables['popularity']` has each repository's stars, forks (whole network) and watchers as GitHub reported them at the last listing, ordered by stars; `tables['languages']` has bytes and share by language over the subject. The series' last value and the table's count can differ (stars since the sync; forks of forks), and the captions say which is which. (Stats spec popularity; tasks 6, 8 and 10)
12. **A user subject's popularity counts the whole repository.** As in `delivery`, every star and fork of a user's repositories counts, since a star is given to a repository, not to the commits of one author. (Stats spec Aggregation; task 7)
13. **Range and empty results.** With no `--since`, the range starts at the earliest record of any requested group, stars and forks included, so `--groups activity,popularity` on a repository starred before its first commit (an import) starts at the first star. The popularity tables come from the repositories themselves, so a popularity request never raises `EmptySubjectError` for lack of records; with no star or fork at all, the range is the one bucket holding `until`. (Stats spec Range and Error handling; task 7)
14. **No popularity breakdowns.** Total series only, as for `flow` and `delivery`; each repository's own counts are in the popularity table. (Stats spec Aggregation; task 6)
15. **Terminal layout.** Three tables after the DORA proxies: Popularity by period (Stars added, Stars total, Forks added, Forks total; a `Total` row sums the added columns and gives the last totals), Popularity now (per repository, with a `Total` row), and Languages (the first 10 rows, then `and N more`). The trend lines gain the four popularity series. (Reports spec Terminal; task 8)
16. **HTML layout.** A Popularity section after Delivery: tiles for Stars, Forks, Watchers and Top language; Stars per period and Forks per period (bars) and Stars over time and Forks over time (lines), each with one y-axis; a Languages chart (horizontal bars of share, the first 10 rows); and the three tables, Popularity by period once per granularity. (Reports spec Static HTML; task 10)
17. **`cache info`, `--groups` help and the web form name the new data.** `CacheInfo` gains `star_events` and `forks`; `--groups`, the web app's `groups` description and the form's hint list `popularity`. (Reports spec Command line and `cache info`; tasks 8 and 9)
18. **Every spec is marked `implemented` at the end.** Step 10 is the last step of the implementation order, so the list's last task sets the status of the system, fetch, stats and reports specs and of the implementation order to `implemented` (reports review 3, choice 16, left the reports spec's status to this list). (Task 12)
19. **One task list, in `agents/tasks/stats/`.** As at steps 6 and 8, the list lives with the spec whose group it builds, as `stats/tasks-4.md`, and carries the fetch and reports work the group needs.
