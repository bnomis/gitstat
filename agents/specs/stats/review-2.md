## Decision

1. **How a sync tells that a repo's pull requests and issues are unchanged.**
   - *Background.* Since step 3, a repo whose listed `pushedAt` and `updatedAt` equal the values stored after its last sync is skipped with no per-repo request. That is exact for commits, because `pushedAt` moves on every push. Nothing in GitHub's documentation says a repository's `pushedAt` or `updatedAt` moves when an issue is opened, a pull request is reviewed or a comment is added, so the same rule would skip repos whose pull requests and issues changed (the shared design rule: a guess needs evidence for it).
   - *What it affects.* The rate-limit cost of every sync that includes `flow`, which the default report does; with `fetch.max_age` at its default of zero, every report syncs.
   - *Option A (recommended): probe in the repo listing.* The listing query also selects each repo's newest pull request's and newest issue's `updatedAt` (`first: 1`, ordered by `UPDATED_AT`), stored on `Repo`. A repo's pull requests (or issues) are skipped when that time is earlier than the stored watermark less `fetch.overlap`, which is exactly when the first page would stop on its first item. The listing costs about 2 points per 100 repos instead of 1; an unchanged repo costs nothing more. Fetch spec 1.5, Incremental sync step 1; tasks 1, 3 and 5.
   - *Option B: always query.* Every sync sends one pull request query and one issue query per repo, about 2 points per repo: an org of 500 repos spends about 1,000 of the 5,000 hourly points per run. Simpler: no new `Repo` fields or listing fields. Choosing it removes the probe fields from the fetch spec, `Repo` and tasks 1 and 3, and the skip rule from task 5.
   - Asked on 2026-10-29 as a decision card in the project thread; the answer is copied below.

## Choices made (approve or flag)

2. **Records.** `PullRequest` gains `updated_at` (the read filter and the "unchanged rows untouched" test need it). `Issue`, which the fetch spec named but never defined, has `repo`, `number`, `author_login`, `created_at`, `updated_at` and `closed_at`. `merged_at` is kept only when GitHub's `state` is `MERGED` and `closed_at` only when it is not `OPEN`, so a reopened issue counts as open from a positive signal rather than from `closedAt` being empty. GitHub's `issues` connection holds no pull requests, so nothing is counted twice. (Fetch spec API; task 1)
3. **First review.** `first_review_at` is the earliest submitted review (states `APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`, `DISMISSED`; a pending review has no submission time) among the first 20, by anyone but the pull request's author and accounts whose GraphQL type is `Bot`. Without the bot rule, an automatic reviewer such as Copilot's would make every review time a few minutes; without the author rule, an author's reply to a review thread (which GitHub stores as a review) would count. A review by a deleted account (author `null`) counts. More than 20 author or bot reviews before the first other one leaves it empty, an accepted limit. (Fetch spec Incremental sync step 2; task 3)
4. **Bot logins in REST form.** GraphQL gives a bot's login without the `[bot]` suffix that REST and `stats.bot_logins` (`dependabot[bot]`) use. The fetch layer stores a `Bot` author as `<login>[bot]`, from GitHub's own type field, so one login means one account across the cache. (Fetch spec Incremental sync step 2; task 3)
5. **The watermark is the `Date` header.** The spec asks for a server-side timestamp taken at the start of the sync. The `Date` header of the first page's response is the one GitHub sends on every response ([RFC 9110, Date](https://www.rfc-editor.org/rfc/rfc9110#name-date)); `GitHubClient.graphql_dated` returns it with the data, and a response without it raises `GraphQLError` rather than falling back to the local clock. (Fetch spec API and Incremental sync step 3; task 2)
6. **A full re-read replaces the repo's rows.** When `fetch.full_refresh_after` has passed or `--full-refresh` is given, every page is read and the repo's rows are replaced in the same transaction as its state, so a deleted or transferred issue leaves the cache (the implementation order's "Done when"). (Fetch spec Incremental sync step 5; task 4)
7. **Reading filters on `updated_at`.** `Fetcher.pull_requests(repo, since)` and `issues(repo, since)` return the rows with `updated_at >= since`. Every event of an item (created, reviewed, merged, closed) is at or before its `updated_at`, so this is a superset of the items with an event in range, and stats filters each metric by its own event date. (Fetch spec API; tasks 1 and 8)
8. **Cache schema 2, no migration.** The new tables and listing fields raise `SCHEMA_VERSION` to 2 and change the listing query's hash, so a cache written by step 5 is refused once with the existing `CacheVersionError` message (`wambatic cache clear`, or `--ignore-cache-version`). This is the spec's own rule for a later table, and the cache is derived data; the README says so. (Fetch spec Cache; tasks 1 and 11)
9. **`cache info` and the sync log name the new resources.** `CacheInfo` gains `pull_requests` and `issues` counts, and the sync log line gives the rows written per resource instead of "commits written". `SyncReport.full_refetches` stays commits-only: a full read of pull requests and issues is routine (first sync, the interval), not a sign of rewritten history. (Fetch spec API, reports spec Running `report` and `cache info`; tasks 1 and 10)
10. **What each flow count counts.** `prs_opened` and `issues_opened` by creation date, `prs_merged` by merge date, `issues_closed` by close date for issues closed now. A pull request closed without merging is in none of them. 1.1 named `time_to_close` without saying of what; it is the issue's open-to-close time, since pull requests have `time_to_merge`. (Stats spec Metric groups; task 7)
11. **Series names and percentiles.** Each duration is two series, `<name>_p50` and `<name>_p90`, in hours, like `workflow_duration_p50` in the delivery group. p90 uses `statistics.quantiles(..., method='inclusive')`, which stays inside the values (the default extrapolates above the largest for small samples, see Automatic checks). PR size is `pr_size_p50` by `statistics.median_low` over pull requests merged in the bucket, so it is one real size and an integer, as the JSON output requires of unit `lines`. Empty buckets have no value, as 1.1 already says for medians. (Stats spec Metric groups; task 7)
12. **Bots are counted in flow.** As in `activity`, `stats.bot_logins` affects contributor counts only, so Dependabot's pull requests count in `prs_opened`, `prs_merged` and `time_to_merge`. Flag this if you want them left out of flow; it is one filter. (Stats spec Metric groups; task 7)
13. **A user subject counts the user's own pull requests and issues.** As with commits, only items whose author is the user, in the user's repositories. (Stats spec Aggregation; task 8)
14. **No flow breakdowns in step 6.** `flow` has total series only; per-repo and per-author breakdowns stay with `activity`. They can be added later without changing the totals. (Stats spec Aggregation; task 7)
15. **Range and empty results across groups.** A `None` `since` starts at the bucket of the earliest record of any requested group. `EmptySubjectError` is raised only when no requested built group has a record in range; a repo with pull requests but no commits in range reports activity as zeros. (Stats spec Range and Error handling; task 8)
16. **Terminal layout for flow.** Two tables after the activity sections: Flow by period (the four counts, with a `Total` row) and Flow times by period (the six duration percentiles in hours with one decimal place, and PR size, `-` for no data, no `Total` row because medians do not add up). Trends gain the four flow counts only. Activity tables appear only when the result has activity series, so `--groups flow` works. (Reports spec Terminal; task 9)
17. **No labels yet.** Pull request labels (and the first commit's time) are what the step 8 hotfix and lead-time proxies need, but nothing in step 6 reads them. They are left to step 8's fetch amendment, which is a schema increase anyway; the implementation order says so. The README's `stats.hotfix_labels` row, which says "for the flow group", is corrected to the delivery group. (Implementation order step 8; task 11)
18. **One task list, in `agents/tasks/stats/`.** Step 6 spans the fetch, stats and reports specs. As step 5's list (in `reports/`) also carried the fetch work it needed, this list lives with the spec whose group it builds, as `stats/tasks-2.md`.
