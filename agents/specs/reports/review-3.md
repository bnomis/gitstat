## Decision

1. **Which server library the web app uses.**
   - *What is being decided.* Whether the web app is built on FastAPI and uvicorn, as the reports spec has named since 1.0, or on the server half of aiohttp, which the project already depends on.
   - *Background.* The spec named FastAPI on 2026-10-29, before the fetch layer was built on aiohttp (step 2). The shared tools-and-libraries rule says to prefer what is already in the project. aiohttp ships a typed server (`aiohttp.web`) and test client (`aiohttp.test_utils`); the fetch tests already serve replayed GitHub responses with `aiohttp.test_utils.TestServer`. The app has four GET routes, and the stats request already has a JSON form (`result_to_dict`), so FastAPI's request models and generated OpenAPI page would describe parameters the app validates with the CLI's own parsers anyway.
   - *What it affects.* `pyproject.toml` and `uv.lock` (new runtime packages or none), `web.py`, the web tests, the system spec's stack line, and tasks 3, 4, 5 and 6.
   - *Option A (recommended): `aiohttp.web`.* No new dependency. `web.py` builds an `aiohttp.web.Application`, `serve` runs it with `aiohttp.web.run_app`, and the tests drive it with `aiohttp.test_utils.TestClient` under `asyncio.run`, like the fetch tests. Sync jobs run on the same event loop as the `Fetcher`, which is aiohttp already. Parameters are parsed by hand with the CLI's parsers, and there is no generated API page; the README documents `/api/stats`. Spec: Module location, Web app, External dependencies; system spec Stack.
   - *Option B: FastAPI with uvicorn.* Adds `fastapi` and `uvicorn` and, through them, `starlette`, `pydantic`, `pydantic-core` (compiled), `anyio`, `click`, `h11`, `opentelemetry-api` and smaller packages. Gives typed query models, automatic 422 responses (which the spec's 400 would have to override) and an OpenAPI page at `/docs`. Tests use Starlette's `TestClient`, which needs `httpx` as a further development dependency. Changes task 3 (a `uv add` subtask and a maintenance check), tasks 4 and 5 (routes as FastAPI handlers, an exception handler mapping 422 to 400) and task 6 (`uvicorn.run`).
   - *Option C: stdlib `http.server`.* No dependency, but a threaded synchronous server: each sync job would need its own thread and event loop beside a `Fetcher` built for one loop, and the spec's progress polling would hold a thread per waiting browser. Changes tasks 3 to 7.
   - Asked on 2026-10-30 as a decision card in the project thread; the answer is copied below.

## Choices made (approve or flag)

2. **The sync-then-compute pipeline moves to `reports/service.py`.** `cli.py` holds target parsing, date parsing, the request builder, `make_fetcher`, `needs_sync`, `log_sync`, `build_result` and the token redaction; the web app needs every one of them, and only the composition roots may import `wambatic.cli` (`test_layering.py`). They move unchanged in behaviour to `wambatic.reports.service`, which `cli.py` and `web.py` both import; `build_result` takes keyword flags instead of the CLI's `Report` dataclass and becomes `build_results`. The layering rule gains one exception: `wambatic.reports.service` and `wambatic.reports.web` may import `wambatic.fetch`, as the spec's "until step 9's web app" already foresaw; every other reports module still may not. (Spec Module location; tasks 2 and 9)
3. **The five-result HTML build moves to `html.py`.** Review 2 left it in `cli.py` and noted step 9 should hoist it. `html.period_requests(request)` gives the five requests (`TOTAL` then year, month, week, day) and `html.html_report(results, initial)` the `HtmlReport`; the CLI and `/report` both call them. (Spec API; task 2)
4. **`Fetcher.sync` reports progress into an optional `SyncProgress`.** The spec's progress endpoint has nothing to read: `sync` returns a `SyncReport` only at the end. `sync` gains a keyword `progress: SyncProgress | None = None`, a small mutable dataclass it updates on the event loop: the repositories listed once the listing is read, how many need a per-repo sync, how many are done, and the rows written so far. No other fetch behaviour changes, and the CLI passes nothing. (Fetch spec API and Implementation; task 1)
5. **A page that needs a sync answers at once with a progress page.** `GET /report` and `GET /api/stats` check freshness as the CLI does (`needs_sync` with `fetch.max_age`). Fresh: they compute and answer 200. Not fresh, or a bare `NAME` to resolve: they start a sync job, or join the one already running for the same subject and resources, and answer 202 with the job's id: an HTML progress page for `/report`, which polls `GET /api/progress?job=ID` once a second and reloads with `&job=ID` when the job is done, or `{"job", "progress"}` JSON for `/api/stats`. A request carrying the id of its own finished job computes without checking freshness again, so with the default `max_age` of zero the reload does not start a second sync. The spec's "worker thread" becomes an asyncio task on the server's loop: the `Fetcher` is async and already runs its SQLite calls on worker threads. (Spec Web app; tasks 3, 4 and 5)
6. **One sync at a time.** Jobs for different subjects queue behind one lock, each reporting `queued` until it starts, so two browser tabs cannot double the concurrency `fetch.workers` allows against GitHub's secondary limits, or contend for the one SQLite writer. Each subject's latest job is kept, so its id stays valid until a new job for that subject replaces it; a failed job is dropped once its error has been shown, so the next request retries. (Spec Web app; task 3)
7. **The query parameters are the CLI's computing flags.** `target`, `by`, `since`, `until`, `groups`, `by_author` and `tz`, parsed by the same code as the flags, so a value the CLI rejects is a 400 here with the same message; `by=total` is a 400 for `/report` (as `--by total` with HTML) and allowed for `/api/stats`. The fetching flags (`--full-refresh`, `--no-fetch`) are not parameters: the server's operator decides how fresh data is, with `serve --max-age`. (Spec Web app; task 4)
8. **Statuses.** 400 for `UsageError`, `SettingsError` (an unknown `tz`) and the request errors of stats (`UnknownGroupError`, `InvalidRangeError`, `InvalidRequestError`); 404 for `NotFoundError` and `EmptySubjectError` (no such target, or nothing in range); 502 with the upstream message for every other `FetchError` (`AuthError`, `RateLimitError`, `GraphQLError`, `StatsPendingError`); 500 with "internal error; see the server log" for anything else, logged with `loguru.logger.exception`. No response carries a traceback or the token. 1.5 named only 400 and 502; 404 keeps "no such repository" from reading as a GitHub outage. (Spec Error handling; tasks 4 and 5)
9. **`serve` takes an optional target.** 1.5 had `serve <target>` and `serve(subject, request, host, port)`, yet `/` is a form for any target. The target becomes optional: given, it is checked at start-up (a bad one is exit status 2), fills the form's default, and the start-up log line names its report URL. `serve` gains `--allow-remote`, `--max-age` and `--ignore-cache-version`, mirroring `report.allow_remote` and the `report` command. (Spec Command line and API; task 6)
10. **What counts as loopback.** `--host` is loopback only when it is exactly `localhost` or an IP address whose `is_loopback` is true (`127.0.0.0/8`, `::1`); every other host, `0.0.0.0` and `::` included, needs `--allow-remote` or `report.allow_remote`, else `serve` exits 2 before binding. A host name other than `localhost` is not resolved to find out, per the shared design rule that an inference needs positive evidence. With remote access allowed, a warning says that anyone who can reach the port acts with the operator's token. (Spec Web app; task 6)
11. **The loopback server checks the `Host` header.** A page on any website can reach `127.0.0.1:8000` through DNS rebinding and read the JSON, which may cover private repositories the operator's token can see. When bound to loopback, a request whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (with the server's port) gets 403. With `--allow-remote` the check is off, since the names the server is reached by are not known. The app sends no CORS headers. (Spec Web app; tasks 4 and 6)
12. **No aiohttp access log.** aiohttp's access log goes through stdlib `logging`, which the shared Python rules exclude. `run_app` gets `access_log=None` and a middleware logs each request at `debug` through loguru (method, path, status, milliseconds). (Spec Web app; tasks 4 and 6)
13. **Stopping.** Ctrl-C stops the server, cancels a running sync (whose state advances per repository, so the next sync resumes, as step 3 built), closes the cache and exits 0, the normal way to stop a server; a port that cannot be bound is exit 1 with the reason. The cache is opened once at start-up, so a `CacheVersionError` stops `serve` with exit 1 before it listens. (Spec Error handling; task 6)
14. **The pages.** `/` is a plain HTML GET form to `/report` that works without script; the progress page shows the job's state and counts and needs script only to poll and reload; both are templates under `reports/templates/` filled with `string.Template`, with every value from the request through `html.escape`, as the static page does. `/report` returns `html_document` with `report.html_theme`, so it is the same page `report --format html` writes. (Spec Web app; task 5)
15. **Tests.** Every route is tested with `aiohttp.test_utils.TestClient` against the stats fixtures' cache, and syncs against the `Upstream` fake GitHub in `tests.fixtures.fetch.upstream`. The step's "large-org fixture does not block the page" is a generated org of a few hundred repositories whose history responses are held back (`Upstream.history_delay`): while its sync runs, `/` and `/api/progress` must answer within a second and the done count must rise. A browser test (`browser` marker, as step 7) opens `/report` on a server in a thread and checks that the progress page turns into the report with every chart drawn. (Spec Web app Testing; tasks 4, 5 and 7)
16. **The reports spec stays `proposed`.** This list builds the last front end, but step 10 adds the languages chart to the reports spec (Visualisation choices), so the step 10 list sets the status. (Task 9)
17. **The README gains a web app section**, its settings table loses "not built yet" for the three web settings, and its exit statuses gain `serve`'s, per the shared user-guides rule. (Task 8)
